# M6b runtime transport audit

Source and SDK audit, not an implementation or a frozen contract. Reviewed against the local Bulwark sources and the currently resolved Windows SDK; no app build, live account, real input, or runtime security claim was made.

## Reference protocol and trust boundary

- `<bulwark>/lib/plugin-sandbox/host-bridge.ts:327-459` creates a background iframe per plugin and an iframe per slot, waits for ready before init, and uses `postMessage` to the frame. Production untrusted frames have opaque origin; every received message checks `event.source === iframe.contentWindow` and `event.origin === 'null'` (`:460-477`). It destroys the instance on a later iframe load (`:427-437`, `:740-771`). Native code should invalidate earlier, at navigation start, rather than permit the interval before load.
- `<bulwark>/lib/plugin-sandbox/runtime.tsx:286-312,1634-1639,1763-1788` pins the parent window and its non-opaque URL origin, checks both on every host message, and transfers an activity `MessagePort` on the first ready. `<bulwark>/lib/plugin-sandbox/sandbox-document.ts:15-63` constructs the sandbox document and serves built runtime assets. The parent URL and sandbox document URL must share an actual trustworthy, non-opaque URL origin for the unchanged runtime's parent-origin check; the **frame security origin** remains opaque under sandboxing.
- Important reference/plan discrepancy: reference `host-bridge.ts:356-370` uses `allow-scripts allow-forms` in production untrusted frames, while M6b-plan Security invariants say `allow-scripts` only. Reference `proxy.ts:464-480` sets `form-action 'none'` and allows script-initiated form handling. Do not silently change the plan: coordinator must decide compatibility/security and test forms. Dev `allow-same-origin` is not the production security model.
- `<bulwark>/lib/plugin-sandbox/protocol.ts:115-250,253-334` defines these sandbox→host variants: `sandbox-ready`, `init-done`, `init-error`, `api-request`, `callback-invoke`, `hook-result`, `theme-applied`, `slot-resize`, `frame-escape`, `slot-should-show-result`, and floating-dropdown `open/update/close`. Host→sandbox: `init`, `api-response`, `callback-response`, `hook-invoke`, `locale-change`, `theme-change`, `settings-change`, `host-change`, `props-update`, `slot-should-show`, `stream-chunk/end/progress`, and floating-dropdown `select/highlight/dismiss`. Implement and validate every variant by direction, state and frame kind; do not treat an unknown type as an API call. The initial ready activity port is an additional transferable, not present in the JSON envelope.
- Structured clone is substantive: `protocol.ts:296-301` and `host-bridge.ts:655-666` transfer stream `ArrayBuffer` chunks; `runtime.tsx:368-407,530-534,602-607,646-666,859-873,1043-1047` uses buffers, views, Blob and streams in both directions. Preserve actual view offset/length, type where required, Blob MIME and zero-byte values; never serialize typed arrays as JSON objects or their entire backing buffer. Preserve transfer detachment where observable in the reference, or record and test any unavoidable exception.

## Installed Windows SDK facts

`src/Barbican.App/obj/project.assets.json:866` resolves Microsoft.Web.WebView2 **1.0.3719.77**; the package contains `lib/Microsoft.Web.WebView2.Core.winmd` and XML documentation for the corresponding Core API. The checked-in `eng/Uno.WebView2Name.targets:3-13` describes a separate Uno Skia naming workaround, not proof of WinRT parity on other heads. Inspect/compile against the actual WinUI projection after the contracts freeze; Linux/WebKit is deferred.

- Installed SDK XML `lib/net462/Microsoft.Web.WebView2.Core.xml:1492-1503,1588-1605` says top-level `CoreWebView2.WebMessageReceived` handles top-level `window.chrome.webview.postMessage`; its object is JSON converted. `PostWebMessageAsJson` sends a JSON value to the top-level document asynchronously, and can be discarded during navigation. Official [CoreWebView2 documentation](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/winrt/microsoft_web_webview2_core/corewebview2?view=webview2-winrt-1.0.2739.15) documents the WinRT surface.
- SDK XML `:2181-2185,4595-4690,4748-4752` documents `FrameCreated`, frame `WebMessageReceived`, frame `PostWebMessageAsJson`, `NavigationStarting`, `Destroyed`, `IsDestroyed`, and nested frame discovery. Frame messages likewise JSON-convert. The official [frame message documentation](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2frame.webmessagereceived?view=webview2-dotnet-1.0.3856.49) confirms frames can post directly when web messaging is enabled. Top-level and frame events are different trust paths; do not assume enabling only the top-level handler removes the iframe's `chrome.webview` object.
- SDK XML `:1496-1502` guarantees message ordering per sending page, not across frames or relative to DOM/navigation events. XML `:1548-1560` documents document-created injection, which applies to frames too: it is unsuitable for distributing native secrets or privileged functions indiscriminately. `IsWebMessageEnabled` and `AreHostObjectsAllowed` are WebView settings, not a demonstrated per-frame security switch. Enforce resource, popup, new-window, download, permission and navigation policies independently. WebView runtime version/behavior and all WinRT signatures must be verified on the shipped runtime, not inferred solely from the SDK package.

## Recommended implementation (design inference)

1. Use a dedicated plugin WebView/profile boundary, preferably one WebView per isolated frame initially. Serve a fixed, read-only **trusted parent trampoline** and reference sandbox assets through a narrowly intercepted non-opaque HTTPS origin with no mail credentials, arbitrary filesystem route, general host API, or live JMAP/network content. The parent creates the intended iframe and keeps its exact WindowProxy; sandbox runtime runs unchanged inside it. Do not give the parent DOM to plugin code, or inject a bridge into all documents. Privileged same-origin plugins are explicitly full trust and need a separately approved execution model; they can access a same-origin parent, so they cannot share a privileged parent bridge or claim untrusted isolation.
2. Only the trusted top-level document may send native RPC. Parent receives `message` and verifies **both** source against its currently mounted `iframe.contentWindow` and expected opaque origin before inspecting, then applies state/direction/schema/type/binary budgets. It accepts the first ready only, holds the transferred activity port privately, and relays rate-limited activity to the native idle coordinator with no user data. Parent→frame uses `iframe.contentWindow.postMessage` (target `*` only for the opaque frame); the unchanged sandbox validates its real parent and origin. Top-level bridge must check expected top-level `Source`, a native-owned WebView/instance/generation and allowed route. Ignore and reject *all* direct iframe WebMessageReceived traffic; plugin-supplied claimed IDs, package hashes, nonces, or `Source` alone are never authority. Never echo native secrets to the frame.
3. Native binds the accepted top-level channel to the host-created `PluginRuntimeBinding` object, immutable package/hash, profile, frame kind/slot, current grant generation and account context. Every request and response rechecks current package installation, revocation, enabled state, account/version and cancellation. IDs correlate only inside that binding; reject duplicate/replayed/out-of-order or unknown responses. Destroy the instance, abort streams, invalidate the generation and reject pending calls synchronously at navigation start, top-level navigation, renderer failure, destruction, uninstall, disable or grant/account change; do not wait for `load`. Apply cancellation/limits again immediately before side effects and before returning bytes.
4. Parent needs an explicit, collision-proof tagged binary codec across the JSON-only native edge: typed tags plus bounded byte payloads (base64 chunks or brokered native buffers), Blob MIME/type, `ArrayBuffer`, exact view range/type, nested values, null versus missing, and error values. Use transfer lists back into the sandbox for chunks; copy only the view slice on input. Blob conversion is asynchronous: preserve per-instance message order and cancellation while it is read. Do not let untrusted data forge a codec tag into a privileged object. Set bounded depth, properties, text lengths, binary-per-message and aggregate per-instance bytes, in-flight requests, callbacks, streams, queue length, lifetime, per-chunk size, backpressure and timeouts; validate actual decoded byte count and sequences and fail closed on truncation. Avoid JS spread/string concatenation on large bytes; no unbounded base64 expansion.
5. Caps at the trampoline and native decoded envelope do **not** stop a hostile iframe from calling `chrome.webview.postMessage` with an enormous object directly: WebView may JSON-serialize/allocate before the host sees an event. Reject iframe events without processing payload, bound per-WebView memory/process lifetime and rate where feasible, and treat transport-level preallocation/renderer crash isolation as an explicit unresolved SDK limitation to test. A shared WebView makes this a denial-of-service risk to all siblings; it must never share the primary mail reader or its profile. CSP and resource interception must prohibit direct network/redirect/private targets while permitting only reviewed bootstrap assets; host-mediated HTTP still enforces grants and URL rules. `'self'` must not accidentally expose privileged native routes to the sandbox.

Direct `CoreWebView2Frame.WebMessageReceived` offers a native frame object and avoids a JS relay, but changes the unchanged runtime's `window.parent`/`event.source` protocol, requires a frame-specific bootstrap or protocol rewrite, still requires the binary codec, and exposes a direct posting surface for hostile frames. Frame object identity and navigation lifecycle would need positive binding and adversarial tests; origin `null`, script-provided identifiers and frame names are not enough. The recommended parent trampoline preserves reference semantics and makes source checks inspectable, but has its own page-compromise and pre-native-serialization risks; neither alternative is safe merely because a random token is present in script.

## Contract and acceptance gates before coding

Current coordinator worktree is mutable: `Core/Plugins/Runtime/PluginRuntimeBinding.cs` already binds package, grant generation, profile, frame kind and lifetime; `IPluginRuntimeInstance.cs` and `Bridge/PluginApiRequest.cs`/`PluginCallOutcome.cs` currently pass `JsonElement`. These are draft seams, not frozen contracts. Define a shared discriminated value/binary ownership contract or a strictly specified tagged JSON envelope plus bounded binary broker *before* freezing; ensure callbacks, hook results, slot props, API results, streams and activity all fit it. Specify what account context is captured/revalidated and dispose/late-message behavior. A message-size check only after `WebMessageAsJson` retrieval is not a renderer allocation limit.

Test unchanged plugin fixtures through real isolated WebView2 instances: all listed message types, binary sizes including offsets/empty blobs/stream boundaries, first-ready activity, duplicate/unknown IDs, wrong frame/origin/sibling/nested frame, top-level and iframe direct `chrome.webview` spoof, large direct payload, navigation-before-delivery, disable/revoke/account switch while awaiting, and controlled teardown/renderer crash. Verify no data or side effects after invalidation, iframe network and redirect denial, no access to mail WebView/host objects, parent origin restrictions, and explicit permission/capability failures. Test visible focus/slot sizing and the actual installed runtime independently. No claim of implementation, Windows runtime proof, or Linux/Uno parity follows from this audit.

## Coordinator review notes

The account context above is captured per operation, not permanently pinned to a background frame: see M6b-account-routing.md. Active-account changes invalidate affected operation/resource snapshots; subsequent background calls follow the newly active login without mandatory runtime restart. Grant/profile/package changes still invalidate their runtime binding. The binary implementation must reconcile view slicing with exact observable offsets/aliasing and must never expose unrelated host buffer bytes; the audit is not a frozen choice of binary representation. Direct-frame preallocation risk remains unproved until actual native tests.
