**Why the frame gates are open.** WGC delivers frames of the hidden off-screen window only after a layout change, and
the scripts force one with a one-pixel resize. In this run, the user had been idle for about 5 hours and the display had
turned off after its 300 s timeout. Every captured frame was therefore pure white. The UI thread also rendered at about
30 Hz instead of the display rate.

`tools/flicker.py` compares each frame with the first and last ones, so it reported 0/0 for those white bursts. It now
counts uniform frames (`empty`, `capture_valid`), so a white burst can no longer pass silently.

"Header and body in one frame" and "no blank between messages" rest on the code: header and reveal are applied in the
same UI turn (`BodyShell.Ready`), and old content is kept until the new page is ready. They do not rest on frames.
Measuring them needs an on-screen or virtual-display run, which needs your OK (ADR 0007 "M0 review").

## 4. HAND TEST 1 (for the user)

Unzip `artifacts/portable/Barbican-6b506bea75e7-win-x64.zip` and run `Barbican.exe`. It uses its own profile
(`%LOCALAPPDATA%/Barbican-dev`). On first start it copies the Rust app's prefs, panes and search history once, and only
reads the Rust folder. Its credentials go to `Barbican.Next/dev/...` and never touch the Rust app's. **Every account is
read-only in M1**: nothing is ever marked read, moved or sent.

1. **Sign in by hand to `<readonly-account>`** (password + one-time code, or OAuth in your real browser). Then add
   `<test-account>` through the avatar menu (Add account). Check:
   - the server lookup;
   - the error texts, for example a wrong password: "Wrong username, password or one-time code.";
   - "Remember me";
   - a restart that restores both accounts without the sign-in screen flashing.
2. **Browse every folder of both accounts.** Check:
   - counts, unread, the storage ring and card;
   - muted (unsubscribed) folders;
   - collapsed parents with the unread dot;
   - date groups;
   - the unread-first Inbox section, if you use the mountain-view layout;
   - load more by scrolling a long folder.
3. **Feel against the Rust app** on `<readonly-account>`:
   - fast switching with j/k and the arrow keys (hold for key repeat);
   - clicking rows;
   - Escape to close the reader;
   - a thread message (the conversation strip shows, but has no click handler yet, I-222);
   - in each case, look for a white/black flash, a blank body, a header that changes before its body, or a dim that
     appears on cached messages.
4. **Theme and style:** Bento and Nordic, dark and light, more contrast. Resize the window narrow and wide. Judge
   against the mockups. Look at the Nordic light icons (§2 Design).
5. **Push:** send a mail to the test account from another client. It should appear as one new row within about 1 s,
   with no list reload. Mark a message read elsewhere: the row updates in place.
6. **Keyboard focus:**
   - typing j in the search box must not move the selection;
   - Enter or Space on a focused button should not also open a message;
   - after clicking into a message body, keys still work, and a click on the list takes focus back (L-047).
7. **Hover-only things:** tooltips on the rail and buttons, row hover states.
8. **Optional live suite** (read-only, `<readonly-account>`). Set `BARBICAN_LIVE=1` with `BARBICAN_LIVE_SERVER`, `_USER`
   and `_SECRET`, then run `tools/build.ps1 test -Project tests/Barbican.Jmap.Live/Barbican.Jmap.Live.csproj`.
9. **Optional on-screen feel run** (ADR 0007): the WGC cadence and the frame gates of §3 need a visible window or a
   virtual display. Only if you agree to it.
10. **Decide** the items in §6.

## 5. Open issues (also in the Fable log)

- **Linux: no run of M1 at all.** This covers:
  - the Uno head (the `win:`-prefixed members are unproven at run time);
  - `SecretServiceStore`;
  - the Linux browser launcher and profile paths;
  - the body shell on Uno (CSP-only blocking; the first `NavigationStarting` is let through);
  - the X11 stand-in overlay, which nothing calls yet.

  Run `tools/linux.ps1 test` and an `xrun` on `m1` once SSH works again.
- **Feel frame gates unproven** (§3).
- **Views not bound to the accounts ViewModels.** `SignInFormModel` and `AccountPopoverModel` drive `IAccountManager`
  directly. So the provider notice, OAuth cancel, the per-account unread badges and the error lines of
  `SignInViewModel`/`AccountsViewModel` are not on screen. The popover refreshes only when the active account changes.
- **`BodyCacheSync` files a sync event under the account active when it is handled.** An event of the old account just
  after a switch can patch the new account's cache, because ids can repeat across accounts. Fix: carry the account key
  in `MailSyncEventArgs`.
- **Two implementations of RFC 8620 §5.6:** `Presentation/Mail/LoadedList.Apply` and `Core/Sync/ListDeltaApplier`.
  A list delta is also applied twice (`ListDeltaEvent` and `EmailsChangedEvent`; harmless, two rebuilds).
- **No test builds the App composition.** A DI cycle hung the first body launch. `SmokeRun` still uses its own probe
  WebView rather than `BodyShell`.
- **`ModelReader` leaves null lists in `EmailBody`.** `BodyShape.Normalize` works around it.
- **Unread-first Inbox** is a local partition, not Rust's two queries.
- **`MailBodyView` never unsubscribes** from `BodyShell.StateChanged`.
- **`IBodyOverlayStrategy` has no caller.**
- **Reviewed-but-unproven on screen:**
  - `shell.js` posts `ready` without waiting a frame, so data: images may decode a frame late;
  - `PopIn` may show its first frame at full opacity.
- **Uno 7 move deferred** (ADR 0004, retry after 2026-11-27).
- **Credential blob limit:** 2560 bytes, about 8 to 10 OAuth accounts in one entry.
