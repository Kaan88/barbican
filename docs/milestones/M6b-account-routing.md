# M6b account routing and runtime context audit

Status: source audit and proposed contracts, not an implemented or frozen interface. Source references below are relative to `<bulwark>` 1.21.2; no live request or test execution was performed. The M6b foundation checkpoint 669ea64 contains immutable package/grant values and four tests only. M6's 583b40d Windows suite passed 2,909 with four skips; it does not prove plugin compatibility. Inspect each method and fixture again when implementing it.

## What the source establishes

- **Instance identity is host-owned, not an account binding.** `lib/plugin-sandbox/host-bridge.ts:1-7,289-342,797-845` creates one background iframe per plugin and one per slot mount. Both initialize with host-selected plugin, tier, manifest and code; only slot mode receives `extraProps`. `host-bridge.ts:464-470,508-516` checks frame source (and privileged origin) and dispatches with the instance's plugin and frame; `host-api.ts:2067-2087` gates each known method by tier and permission. A plugin-supplied plugin ID, account ID or callback ID must not select another instance or grant. `permissions.ts:27-37,71-114` requires manifest and consent except implicit permissions and separately filters slot data by read permissions. `components/plugins/plugin-iframe-slot.tsx:334-344` filters current props before mounting/updating. UI placement permission alone does not grant the underlying mail or account data.
- **The default is resolved at call time.** `host-api-input.ts:25-30` obtains `useAuthStore.getState().client` when a handler calls `sessionClient`, and errors if absent. The instance payload above contains no fixed account. Both background and slot API calls use that same dispatcher, so slot props do not by themselves change generic method routing. `stores/auth-store.ts:4189` emits `onAccountSwitch` with new and previous IDs; `plugin-hook-catalog.ts:281` describes it as after activation. This supports an inference that subsequent default calls follow the active login without necessarily restarting the background frame. The audited snippets do not prove every pending call is cancelled, that all stores switch atomically, or that every runtime survives every switch; test those cases rather than claim them.
- **Two account namespaces matter.** `host-api.ts:475-494,2217-2218` exposes `user.getAccounts()` from local account entries with active/default/connected flags; `host-api-account.ts:47-89` exposes `user.getSelf()` and `user.getMailAccounts()` from the current login's JMAP session, including personal/group/shared and read-only/open flags. Local login IDs are not interchangeable with JMAP account IDs. `host-api-account.ts:92-97` defaults a named account to the login's own JMAP account and accepts explicit IDs only among that login's discovered mail accounts. Directory and account-data handlers use this validation (`:189-206,235-266`). These lists and a method permission do not grant arbitrary other-login access.
- **Mail has method-specific owner resolution.** `host-api-mail.ts:23-66,86-93` uses the current login; absent an explicit account, a listed message may resolve to its known owner, otherwise the selected own message or own account is used. A row from another login is not silently read through the current client. Explicit JMAP account IDs are accepted only when the current login's known shared mailbox or listed row establishes that owner. `:107-137,172-183` resolves a named mailbox to its owner for list/search. IDs can collide, so do not replace this with a global ID lookup. `runtime.tsx:1007-1013` tells plugins to pass a view's accountId when needed. Authorization/read-only and actual JMAP response still control access; an ID claimed by a plugin is not evidence of entitlement.
- **Calendar and tasks use the active session but may target shared resources.** `host-api-calendar.ts:260-261,297-300,330-352,364-385,469-500` calls `sessionClient` and resolves shared event identifiers through that client; it does not prove arbitrary local-login selection through an event ID. Mutation paths validate the event/calendar and use its corresponding store (`:524-557,890-905,978-1017`). `stores/calendar-store.ts:56-70,93-104,123-174` distinguishes local-login ownership from a shared server account and can resolve a connected client for `localAccountId`; do not conflate this store facility with a general sandbox account parameter. Audit each calendar method and its resource rights before implementing it.
- **Composer is a host-registered object capability.** `composer-registry.ts:1-7,24-37,62-96` registers an open composer under an opaque random ID and unregisters it on close. Slot props or action click context carry that ID; account and identity metadata stay host-side. A snapshot revision fingerprints body and metadata including account, but returns the permitted draft fields, not account credentials. `host-api-composer.ts:29-32,71-81,107-134` checks the open handle, optional expected revision, attachment membership and post-read revision. The reference uses a registry lookup for an ID, not an explicit per-plugin ownership check in this function; the ID's host delivery and method permission are the observed boundary. Preserve legitimate background action and slot calls while ensuring host-issued handles cannot be forged, reused after disposal or redirected to another account. `host-api-compose.ts:79-101,115-150` distinguishes opening a compose surface, reply to the open message and draft creation on the session client/default identity; do not treat these as one generic composer operation.
- **Callbacks are frame-scoped and replaceable.** `host-bridge.ts:318-343,521-530,718-734,757-763` stores encoded host callback references in the owning instance, rejects unknown IDs, removes previous prop callbacks on update and clears them on disposal. Slot data is projected before delivery. Background hooks/actions use separately registered callbacks; `runtime.tsx:879-894` describes action context. `onAccountSwitch` is an observer, not a proof of cancellation or authority. Preserve source behavior and add host-side lifecycle checks for pending callbacks and already-issued operations.

## Proposed Barbican contracts (implementation decisions, not claimed source facts)

1. **Instance context:** host-created opaque instance ID, verified package/version, immutable granted permissions/tier, profile and frame kind, and revocable lifetime. Slot context includes only permission-projected host data and host-minted callbacks; it may identify a resource/composer but is not a universal account override. Never consume identity or grants from RPC payload. An untrusted/removed/disposed frame cannot issue or receive new privileged calls.
2. **Call context:** at dispatch capture the current authorized local login, its session generation, client/session handle and operation cancellation/lifetime; resolve omitted account by each method's reference semantics, not a single hard-coded global rule. Model explicit shared JMAP account separately from local login and validate against the captured session's known accounts, capabilities and access rights. For source methods which intentionally accept an explicit alternate login, add a documented allowlisted resolver; do not imply every method accepts one. Keep account and authorization checks current at write/commit, particularly after sign-out, permission revocation or A-to-B-to-A. A request already dispatched may finish against its captured client; drop stale UI/callback delivery, and report ambiguous writes honestly. This generation fence is a Barbican safety proposal, not a claim Bulwark applies one everywhere.
3. **Resource context:** host-issued opaque composer, action and callback handles map to actual live host objects, account/session generation, projected fields and disposal state. Scope handle resolution to its authorized exposure and operation permission, but retain normal background `onAction` use of a composer handle delivered by host; do not require a slot frame for it. Capture coherent snapshot/revision and validate async attachments before and after await. Replacing slot props revokes old prop callbacks; queued calls from stale contexts cannot target a newly active account or colliding resource ID.
4. **Switch and selection:** update the active-session provider on account activation, notify the lifecycle observer as the catalogue specifies, invalidate old account-scoped UI and pending results without needlessly disabling the plugin. Explicitly distinguish active login, default login, open shared mailbox and composer owner. Account lists may include several logins while `getMailAccounts` lists JMAP accounts of the captured login. Preserve reference-compatible outputs and permissions, with privacy projection; never hand out underlying credentials.

Add representative tests against real dispatch and fake sessions: background call before/after switch; slot for a non-active composer; two logins with colliding mail IDs; explicit known shared account vs unknown or other login; current login changes while async calls are pending and A-to-B-to-A; account removal and revoked plugin grant; account list vs mail account projection; shared calendar/resource resolution; stale and disposed composer IDs; changing composer account or revision mid-attachment; background action and slot callbacks; callback replacement/disposal and forged IDs.
