# M6b package authority: source audit and proposed contracts

Status: source audit for coordinator review, not a frozen contract or an implementation. Reference tree is the local Bulwark 1.21.2 source (`webmail-main`); Barbican source is the coordinator's active C# tree. No plugin was loaded, no account was contacted, and no build was run for this audit. Line numbers below identify the upstream sources inspected; line numbers may move in later revisions.

## Separate identity, authority and data

* **Stable plugin ID** identifies the installed record, user settings and plugin data. Bulwark stores bundle code by plugin ID in IndexedDB (`lib/plugin-storage.ts:5-16,124-137`). An uploaded update with the same ID deactivates the old instance, replaces its bundle and manifest, starts disabled, and retains `existing.settings`; it does not erase the `plugin:<id>:` storage namespace (`stores/plugin-store.ts:188-265`). A user upload cannot claim an admin-managed ID (`:202-211`). Uninstall removes code, plugin-scoped local storage for all accounts, hooks, offers and attempts credential cleanup (`:269-276,496-516`). Some cleanup is asynchronous: this is the intended lifecycle, not proof that every external deletion succeeded.
* **Executable/content authority** is a different identity. `bundleHash` is SHA-256 of the JS source, used to detect same-version code changes and check loading (`stores/plugin-store.ts:217-221,710-718`; `lib/plugin-sandbox/bundle-integrity.ts:56-80`; `loader.ts:110-151`). Bulwark's admin **approvalHash** is SHA-256 of UTF-8 `canonicalJson(validatedManifest) + "\n" + code`; its canonical JSON sorts object keys recursively and preserves array order (`lib/extension-package.ts:517-536`). It is not SHA-256 of ZIP bytes, and neither code-only hash nor approval hash covers arbitrary unused ZIP assets. A Barbican whole-package hash may be stricter, but must be named separately; it cannot be sent as Bulwark's approvalHash. Manifest-plus-code canonicalization must have cross-language fixture vectors, including Unicode, numbers and optional fields.
* **User consent** is not data ownership. For an uploaded replacement the new installed record keeps settings but does not copy `grantedPermissions`, so enable asks for declared non-implicit permissions again (`stores/plugin-store.ts:224-247,280-320`). Consent includes HTTP origins and POST paths (`lib/plugin-sandbox/consent.ts:8-16,34-47`). `ui:observe` and `app:lifecycle` are implicit (`lib/plugin-types.ts:1761`; `permissions.ts:27-37`). Admin approval, where policy requires it, is checked against the package approval hash (`plugin-store.ts:873-905`). Managed updates spread existing local record and overlay server metadata (`:700-768`); keystore is special and prompts separately if newly needed (`:518-532`).

Proposed Barbican model: key persistent plugin settings and data by stable ID and the appropriate local-login scope, never by package content hash; bind each executable generation, explicit grants and running frames to an immutable validated package identity/hash. A replacement must receive the required consent before activation and invalidate old generation handles, but keep existing data when consent is granted. A declined/failed/cancelled replacement must not delete or transfer the previous package's data, and must not silently activate new bytes. Bind origin/path allowances and trust provenance to the exact approved manifest as well as permissions. These are stricter security contracts than upstream's per-record consent and must be implemented explicitly, not claimed as exact upstream persistence.

## Local login, storage and settings

Bulwark `api.storage.get/set/remove/keys` dispatches on plugin ID without a separate storage permission (`lib/plugin-sandbox/runtime.tsx:555-560`; `host-api.ts:134-137,2136-2139`). `storagePrefix` selects `useAccountStore.activeAccountId` and composes `plugin:<pluginId>:@<encoded-login-id>:`; legacy unscoped keys are claimed once by the first account using the plugin (`host-api.ts:407-446`; `storage-scope.ts:17-65`). This account is the local signed-in login identity generated from login/server, not an arbitrary shared JMAP resource account ID (`stores/account-store.ts:125,290`; `stores/auth-store.ts:1777-1790`). A shared mailbox selection must not change the storage namespace or authorize another login. Per-login sign-out clears that login's keys; full sign-out clears all plugin storage (`auth-store.ts:1713,2798,2947`; `storage-scope.ts:82-100`). Host-only plugin keys have a separate inaccessible `!` namespace (`storage-scope.ts:68-78`).

Storage values are JSON, `get` returns null for missing/unparseable data, `set` requires a 1-256 character key, and each plugin/login namespace has a 1,048,576 UTF-16-code-unit quota including keys and JSON (`host-api.ts:414-447`). Preserve namespace boundaries under concurrency, validate JSON and quota before commit, and never expose host-only metadata as plugin keys. The upstream runtime calls this surface `api.storage`; the audit found no separate `api.userStorage` API. If Barbican uses `userStorage` as an internal contract name, map it explicitly to `api.storage` rather than inventing a different public JS API.

`api.plugin.settings` is a live object initialized from effective settings; `onSettingsChange` callbacks see the same object updated in place (`runtime.tsx:77-80,145-152,486-498,1712-1713`). Schema defaults and stored values are merged/coerced: unknown stored fields are hidden when a schema exists; invalid types fall back to default, selects require an option, numbers clamp (`lib/plugin-settings.ts:5-47`). Settings updates notify running instances (`stores/plugin-store.ts:350-365,930-940`). Upstream persists these settings in its browser-wide installed-plugin record (`:467-478`), not separately per simultaneous login; full sign-out resets user-installed settings and grants, disables them, and retains code (`:942-963`). A local-login-keyed Barbican settings design is a deliberate isolation improvement, not an upstream fact. Decide and test sign-out deletion versus retention explicitly; do not let a package hash change erase values during an authorized update.

## Package validation and compatibility

Bulwark's plugin manifest requires stable `id`, `name`, `version`, `author`, `type`; description defaults empty; supported types are `ui-extension`, `sidebar-app`, `hook`; default entrypoint is `index.js`. ID is lowercase alphanumeric/hyphen, length 2-64; version is dotted numeric with optional suffix; safe entrypoint is a relative `.js`/`.mjs` path without empty, dot or parent segments. Validated output retains the known manifest fields including permissions, tier, minAppVersion, settingsSchema, configSchema, locales, frameOrigins, httpOrigins, apiPostPaths and credentials (`lib/extension-package.ts:176-220,401-499`; `lib/plugin-types.ts:129-218`). Unknown required permissions fail; unknown optional permissions warn and are omitted; deprecated ones are dropped; known optional permissions join the consent set. ZIP limit is 5 MiB compressed, at most 200 entries, manifest 512 KiB inflated and individual reads 20 MiB; actual inflated bytes are counted (`plugin-types.ts:1768,1777-1780`; `extension-package.ts:31-34,50-96,143-165`). The root may be the archive root or a single enclosing directory. Suspicious JS patterns produce warnings, not a security sandbox (`:502-514`). Barbican should additionally reject ambiguous/duplicate or escaping paths and enforce bounded decompression rather than extract untrusted paths to the filesystem; label any stricter rule as such.

Upstream checks `minAppVersion` against `NEXT_PUBLIC_APP_VERSION` when both parse as `major.minor.patch`; numeric components compare while prerelease/build suffixes are ignored (`extension-package.ts:209-220,470-473`; `plugin-validator.ts:57-64`; `next.config.ts:232`). The unchanged `integration/fixtures/plugin-api-probe/manifest.json` requires `1.15.0`, and the inspected source is Bulwark 1.21.2. Barbican's product version 0.1 is not on that version line. Proposed separate `BulwarkApiCompatibilityVersion`/capability profile for manifest checks; retain the real product identity/version separately. Do not blindly advertise 1.21.2 until its host API is actually implemented and tested, and do not turn off compatibility checks. Boundary fixtures: compatible 1.15 package loads unchanged when the required APIs are implemented; greater unsupported minimum refuses; invalid minimum refuses; suffix comparison matches upstream; native API version remains independent. Upstream `api.app.getInfo` returns its webmail version (`host-api.ts:1997-2004`); decide explicitly how Barbican reports product versus compatibility information rather than accidentally presenting 0.1 as a Bulwark API version.

## Managed signatures, native code and keystore

`managed`, `forceEnabled`, `defaultOn`, `chosen`, `adminApproved`, `bundleHash`, `approvalHash`, permissions, settings/schema and declared network scopes are installed-record or server-owned metadata, not things an untrusted package may self-assert (`plugin-types.ts:255-318`; `plugin-store.ts:578-595,653-783`). Managed sync re-fetches on missing bundle, changed version or changed code hash and removes previously managed plugins absent from the server. User upload under a managed ID is refused. Never turn an untrusted local package into managed/forced/privileged merely from its manifest.

Managed bundle fetch verifies a present `X-Bundle-Signature` as Ed25519 over UTF-8 code with the host public key; an absent signature is tolerated for legacy **untrusted** managed bundles, while privileged requires a valid signature (`lib/plugin-sandbox/bundle-fetch.ts:23-70`; `bundle-signing.ts:1-16,39-55,109-135`; `tier.ts:24-58`). SHA-256 integrity is a separate check. The signature described here covers code, not the validated manifest; server registry provenance and protected metadata must be considered separately. Privileged additionally requires managed provenance and `crypto:full`; unapproved user-uploaded privileged packages are refused, never silently downgraded. Ordinary user-uploaded bundles need no upstream server signature and instead go through user consent and any configured admin approval. Native .NET packages are a different format and trust boundary: current `Barbican.Plugins.PluginManifest` is `(Api, Id, Name, Version, Description, Hooks)`; the host currently loads and instantiates a plugin before reading its manifest (`src/Barbican.Core/Plugins/Native/NativePluginHost.cs:280-326,344-356`). AssemblyLoadContext is not a sandbox. Authenticate/approve third-party executable bytes and establish their provenance before loading any code; preserve separately trusted bundled spam-score. Do not infer native signed/managed status from a JS manifest field.

`api.keystore` is the desktop OS certificate/smart-card API, not a plugin key-value secret store: list/sign/decrypt/agree with native prompts and no private-key export (`lib/plugin-sandbox/runtime.tsx:512-535`; `host-api-keystore.ts:1-12,28-55,111-143`). It is reachable only on supported desktop policy, privileged tier and declared/granted `keystore`; this permission always needs individual user consent even for managed plugins (`permissions.ts:7-11,27-37`; `plugin-store.ts:518-532`). `quiet` must not open a prompt; supported schemes, bounded inputs, user-presence/policy checks and `keystore:*` error codes are part of the interface. Windows consent is separate from package signing and from application Credential Manager storage. If the native helper is unavailable, report feature absence/unsupported and refuse operations; never return a private key or pretend a grant exists. Account sign-out resets session keystore grants (`lib/desktop/keystore-grants.ts:3-11`); preserve host-owned key material boundaries.

## Acceptance checks before freezing

1. Install an unchanged Bulwark fixture requiring 1.15 with a truthful compatible host profile; separately reject a newer minimum and malformed versions. Test a real `.zip` with nested root, declared schema/origin/optional permissions and adversarial paths/inflation; verify exact documented hashes against upstream vectors.
2. For same ID and different package hash, require fresh package-bound authorization and revoke old generation/frame calls; preserve that login's settings and `api.storage` on consented replacement. On rejection/failure, preserve old package, settings and data; no silent authority upgrade. Test changed permissions/origins, same version/new bytes, same code/new manifest and re-zip cases independently.
3. Two local logins stay isolated even if their shared JMAP resource IDs collide; selecting a shared mailbox never changes the login namespace. Sign-out/uninstall behavior is explicit and verified, including failed cleanup and restart. Host-owned keys cannot be enumerated or overwritten by plugins.
4. Managed provenance and signatures cannot be forged by package JSON; reject bad signature/hash and unsigned privileged code, prevent a local ID collision with managed data, enforce policy/revocation at use time. Tests distinguish upstream-compatible unsigned untrusted managed handling from any intentionally stricter Barbican rule.
5. Keystore is separately consented and feature/policy gated, with quiet/no-prompt and no-private-key-export cases. Native code is never instantiated merely to discover a manifest before its executable trust decision. No live account or native key operation is needed for these tests.
