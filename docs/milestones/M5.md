## What shipped

- **Contacts data (con-data).** vCard 2.1/3.0/4.0 reader and writer with hostile-input limits (G-012), form rows and the patch the form owns, dates, photos (Skia, shrunk and
  re-encoded), merge plan, import, the contact store with /changes and push, the writer with its hooks and rollback, address books, groups, the directory (Principal/query
  with a Principal/get fallback), the lookup the mail side uses, the composer's recipient source decorated with contacts and groups.
- **Contacts UI (con-ui).** The Contacts app in the shell (sidebar, list, detail, form, group, import, merge, directory and print dialogs, menus, commands, keys), the reader's
  contact card in the sender panel.
- **Files data (files-data).** FileNode store (draft-18 and the Stalwart 1.0 shapes), the writer with dated trash batches, transfers (upload with conflicts, download, zip), name rules.
- **Files UI (files-ui).** The Files app in the shell (sidebar tree and places, list and grid, details, preview modal, conflict and move dialogs, undo toast, menus, commands, picker).
- **webview-bg.** The mail body WebView2 releases its resources while the window is hidden (D-WV-01).
- **Integration (this pass).**
  - *Wiring.* DI registers the real con-data and files-data services (`AddBarbicanContactsData`, `AddBarbicanFilesData`); the con-ui and files-ui "not available yet" catch paths
    are dead code now (nothing in Core throws `PortPendingException` for contacts or files). A picked photo goes through `IContactPhotos`; the detail pane downloads a blob photo;
    the Files trash place reads `FileTrash.Items`; `ContactFields.Build` returns a patch (create drops the nulls, update diffs it) and `ImportAsync` returns `FailPartial` with the
    count, which the import dialog reads ("Imported N of M, then: ...").
  - *Bugs the real services and the live run found.* (1) The form's patch nulled every stored property the form result lacked (media, localizations, calendars ...): data loss on every
    edit of a card that had one (D-M5-I01). (2) The contact avatar closed its own stream before decoding, so no photo ever drew. (3) The real `FileStore` read `files.json` on the
    UI thread while the sidebar was built: `IoThreadCheck` ended the app (it now reads on the pool from the constructor). (4) The real store raises `Changed` on the thread that
    finished a write, and the Files views redrew on it: an upload ended in "interface marshalled for a different thread" (the view model now posts to the dispatcher).
    The sample store raises on the UI thread, which is why neither showed in the earlier hidden runs.
  - *FakeJmap arms con-data could not add* (D-M5-I09): `SharedContacts`, contacts push through `PushHub.Attach`, `Principals` with Principal/query and Principal/get; tests for shared
    books in the store and writer, the directory against the fake server, and a server-made contact push (`ContactSharedDirectoryPushTests`).
  - *Looks.* The Files sidebar matches the calendar and contacts ones (rounded New pill, tiles or plain rows, borderless rows), the list header and breadcrumb are no longer bordered
    boxes, the upload conflict dialog uses the same pills. Week grid: overlap lanes cascade when side by side would be narrower than 64 px, on an opaque ground, so titles stay
    readable. Mini month: the busy dot sits under the digit.
  - *Leftovers done* (D-M5-I06..I08): reader attachment preview (I-228) with the `onAttachmentPreview` transform, the sender name popover (I-204), Call links on phone numbers (I-205).
- Screens (sample data only) in [M5-screens/](M5-screens/): `int-con-detail-photo`, `int-con-import`, `int-con-merge`, `int-con-directory`, `int-con-print-preview`,
  `int-files-list`, `int-files-conflict`, `int-files-trash`, `int-files-preview`, `int-cal-week` (the earlier `con-*` are con-ui's).
